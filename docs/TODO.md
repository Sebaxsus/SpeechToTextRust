### Gaps nuevos detectados al implementar/probar Fase 6 (no bloqueantes, pendientes)

- [ ] **Bearer token opcional en vez de obligatorio**: hoy `main.rs` sigue bindeando `0.0.0.0` (heredado de antes de Fase 6) y nada impide levantar el servidor sin `MCP_BEARER_TOKEN` configurado — solo hay una advertencia por consola. Antes de exponer de verdad en LAN, decidir si el servidor debería directamente rechazar arrancar (o rechazar bindear algo distinto de `127.0.0.1`) sin el token, en vez de confiar en que quien lo despliega vea el warning.
- [ ] **`allowed_hosts` de `rmcp` sigue limitado a localhost**: `StreamableHttpServerConfig::default()` trae `allowed_hosts: ["localhost", "127.0.0.1", "::1"]` (protección anti DNS-rebinding del propio SDK). Mientras no se amplíe con `.with_allowed_hosts([...])` a la IP de LAN real, un cliente conectando por esa IP va a recibir `403 Forbidden` — prerrequisito adicional a la exposición en LAN, además del bearer token.
- [ ] **`get_audio_metadata`/`list_audios` exponen rutas de disco internas**: el `job.json` que devuelven tal cual incluye `audio_path`/`transcript_path`/`checkpoint_path` (rutas locales del filesystem del servidor, ej. `./jobs/{job_id}/audio.mp4`). Verificado en la prueba manual de esta iteración. No es una fuga de datos sensibles (son rutas relativas fijas, no contienen secretos), pero sí es estructura interna que un cliente LAN no necesita — evaluar si conviene filtrar esos 3 campos antes de responder, dejando solo `job_id`/`status`/`created_at`.
- [ ] **`job.json.status` queda en `Pending` para siempre**: gap pre-existente (ver Housekeeping, "no marca el job como Failed"), pero ahora es directamente visible a través de `get_audio_metadata`/`list_audios` — un cliente MCP no puede hoy distinguir "recién subido" de "transcripción + embeddings ya terminados" mirando el `status`. Esto le resta utilidad real a las dos tools de listado/metadata. Implica actualizar `job.json` a `Processing`/`Completed`/`Failed` en los puntos de transición de `audio_handler.rs`/`run_pipeline`.
- [ ] **Sesiones MCP sin política de expiración**: `LocalSessionManager` (default de `rmcp`) mantiene cada sesión abierta por `initialize` en memoria hasta que el cliente cierra la conexión — no hay timeout de inactividad ni límite de sesiones concurrentes. En un servidor de larga duración (el caso de uso real del proyecto) esto puede acumular estado indefinidamente, algo que `CLAUDE.local.md` ya prohíbe explícitamente para el resto del pipeline ("no diseñar soluciones que... acumulen... en memoria"). Evaluar un timeout de sesión o un límite razonable.
- [ ] **Sin `CancellationToken` propio ni graceful shutdown**: `mcp::build_service` usa `StreamableHttpServerConfig::default()` (que crea su propio `CancellationToken` interno, nunca cancelado desde `main.rs`) y `axum::serve` tampoco tiene `with_graceful_shutdown`. Al matar el proceso, las sesiones MCP abiertas no se cierran de forma prolija (a diferencia de los ejemplos de referencia de `rmcp`, que sí cablean `ctrl_c` → `ct.cancel()`).
- [ ] **Solo probado con `curl`/REST Client (JSON-RPC crudo a mano), nunca con un cliente MCP real**: falta validar contra un cliente que implemente el SDK completo (Claude Desktop, `@modelcontextprotocol/inspector`, u otro) — un curl bien formado no garantiza que un cliente real negocie capacidades, reintente, o maneje la sesión de la misma forma.
- [ ] **CORS no configurado**: si la futura interfaz web (todavía no implementada) va a llamar a `/mcp` directo desde JS en el browser (en vez de a través de un backend propio), Streamable HTTP va a necesitar headers CORS (`Access-Control-Allow-Origin`, exponer `Mcp-Session-Id`) — hoy no hay ningún layer de CORS en el router.
- [ ] (Opcional) WebSocket + TLS (`axum-server` + `rustls`) para conversación multi-turno con streaming, separado del transporte MCP.
- [ ] Interfaz web todavía no existe (fuera del alcance de esta iteración) — el único consumidor probado hoy es HTTP directo (curl / REST Client), no un cliente MCP real ni la UI propia del proyecto.
- [ ] **Diseño a tener en cuenta quando se empiece la interfaz web: el `job_id`/`audio_id` activo tiene que ser un concepto de primera clase en la UI, no un detalle interno.** Todo el diseño de Fase 5/6 gira alrededor de `SearchScope::Audio(audio_id)` como default explícito (ver `CLAUDE.local.md`: "Scope forzado, sin default implícito a todo el corpus") — eso significa que la UI necesita, como mínimo: (1) un selector/listado de audios procesados (`list_audios`) donde el usuario elija con cuál transcripción está trabajando, (2) mostrar de forma visible cuál es el `audio_id` activo en la sesión de chat/consulta actual (no asumido implícitamente), y (3) un control explícito para "salir" del audio seleccionado y pasar a `AllCorpus`, en vez de que sea el estado por default. Esto se vuelve más importante todavía una vez que exista el endpoint de resume (ver Fase 3 más arriba): el usuario también va a necesitar identificar cuál `job_id` quedó a medio procesar para poder resumirlo.
  - [ ] Relacionado — hoy `job.json` no tiene ningún campo "amigable" para mostrar en un selector (solo `job_id` como UUID crudo, sin nombre de archivo original ni título). ## Gaps de robustez detectados en revisión de código (2026-07-29)

Detectados auditando el código real (no solo los docs) a pedido explícito del usuario, buscando memory-unsafety, procesos/conexiones no cerrados, y concurrencia no acotada.

- [ ] **Sin gate de concurrencia entre RAG/MCP y la transcripción — el hallazgo más importante, discusión de diseño pendiente, no implementado todavía.** `transcription_semaphore` (`state.rs`) solo protege `POST /api/upload-audio`/`resume`. Las tools MCP `rag_answer` (`rag::generation`, llama a Ollama con el modelo de 7-8B) y el reranker (`rag::reranker`, cross-encoder in-process vía `candle`, CPU-bound) no pasan por ningún semáforo — se verificó leyendo `generation.rs`/`reranker.rs` completos, cero sincronización. Esto viola directamente "NO paralelismo agresivo... evitar CPU thrashing" de `CLAUDE.local.md`: hoy es posible correr Whisper + generación RAG + reranker simultáneamente, y tampoco hay límite a cuántas llamadas RAG concurrentes se apilan entre sí (dos `AllCorpus` en paralelo, por ejemplo). Acordado con el usuario: lo más probable es que la solución respete la regla general de "una sola carga pesada a la vez" en todo el proceso — a decidir en una discusión de diseño aparte si eso significa reusar el mismo `transcription_semaphore` (Whisper y RAG comparten el único permiso) o un semáforo separado con la misma cardinalidad de 1.
- [x] **Proceso `ffmpeg` no se mataba en paths de error (`decoder.rs`) — corregido.** No había `impl Drop` para `Source::Ffmpeg`; `child.wait()` solo ocurría en el camino de EOF (`pump`) o en un seek explícito (`kill()`+`wait()` manual). Cualquier otro corte del pipeline (Whisper falla un chunk, panic, error de decode) dropeaba `StreamingDecoder` sin matar el proceso — en Rust, dropear un `std::process::Child` **no** termina el proceso, solo cierra el handle; el ffmpeg podía quedar corriendo huérfano indefinidamente en un audio de 5h. Corregido con `impl Drop for Source` (antes de `PumpOutcome` en `decoder.rs`) que llama `kill()`+`wait()` incondicionalmente — ambas llamadas ignoran su resultado (`let _ = ...`) porque en los caminos ya cubiertos (EOF, seek) el proceso ya terminó y ambas fallan de forma esperada; el `Drop` es una red de seguridad, no la única vía de limpieza.
- [x] **Escrituras no atómicas a `checkpoint.json`/`job.json` — corregido.** `CheckpointManager::save` y `create_job` usaban `fs::write` directo; un crash a mitad de esa escritura corrompe el JSON, y `CheckpointManager::load()` fallaría a parsear — `run_pipeline` no arrancaría ni siquiera desde cero, un resultado peor que no tener checkpoint (justo el escenario de "crash a mitad de camino" que Fase 3 existe para tolerar). Corregido con un helper compartido `audio_pipeline::util::write_atomic` (escribe a `{path}.tmp`, después `rename` — atómico en el mismo filesystem, tanto Windows como Linux), usado por ambos call sites. Mismo helper a reusar cuando se implemente `update_job_status` (ver ítem de status más abajo).
- [ ] **Reranker: `unsafe` mmap sin gate de concurrencia (`reranker.rs:67`).** El `unsafe` de `VarBuilder::from_mmaped_safetensors` es inherente a cómo `candle`/`safetensors` cargan pesos por mmap (no es un bug propio del proyecto), pero sin resolver el punto de concurrencia de arriba no hay límite a cuántas llamadas concurrentes a `AllCorpus` mmapean/materializan su propia copia de los ~2.2GB del modelo en f32 — no está verificado si `VarBuilder` comparte páginas mmap entre llamadas o materializa tensores propios por llamada (si es lo segundo, el consumo real de RAM se multiplica por llamada concurrente). Se resuelve como efecto colateral de resolver el gate de concurrencia de arriba, no necesita su propio fix.

## Prerequisito bloqueante — `job.json.status` nunca se actualiza (2026-07-29)

Detectado documentando `docs/api_reference.md`: `status` queda fijo en `"Pending"` desde `create_job` para siempre — ni `run_pipeline` ni `run_embedding_phase` lo tocan en ninguna transición real. Se separa como ítem de nivel más alto (no dentro de la lista de endpoints nuevos de abajo) porque **varios de esos endpoints dependen de este fix para ser útiles** — implementarlos antes que esto solo movería el problema (un endpoint de status que siempre devuelve `"Pending"` no sirve para polling).

- [ ] Actualizar `job.json` en las transiciones reales:
  - `Processing` al arrancar `run_pipeline` (o al adquirir el permiso del `transcription_semaphore`, antes de empezar a decodificar).
  - `Completed` cuando `run_embedding_phase` termina en `Ok(())`.
  - `Failed` cuando `run_pipeline` o `run_embedding_phase` devuelven `Err` (hoy ese caso solo se loguea con `eprintln!` en `audio_handler.rs`, ver Housekeeping más abajo — este ítem es la contraparte de persistir ese fallo en `job.json`, no solo en logs).
- [ ] Diseño sugerido: un helper `audio_pipeline::job::update_job_status(job_id, status)` que lea el `job.json` existente, mute solo el campo `status`, y reescriba — evitar reconstruir `JobMetadata` a mano en cada call site (riesgo de pisar `audio_path`/`transcript_path`/`checkpoint_path`/`created_at` con datos stale).
- [ ] Sirve igual para jobs nuevos (`recibir_y_procesar_audio`) y reanudados (`reanudar_job`) — ambos pasan por `lanzar_procesamiento_job`, un solo punto de instrumentación.
- [ ] Prerequisito directo de: `GET /api/jobs/{job_id}`, `GET /api/jobs`, y cualquier mejora futura a `list_audios`/`get_audio_metadata` de MCP que quiera exponer un status confiable.
- [ ] **Campo adicional `transcript_ready: bool` en `JobMetadata` (no un 5to valor de `JobStatus`)** — decidido tras revisar `pipeline.rs`/`checkpoint.rs`: `checkpoint.json` **no** alcanza para derivar esto porque solo guarda `(last_chunk, processed_seconds)`, sin duración total ni flag de "terminado" — se reescribe igual en el chunk 3 de 5 que en el 5 de 5, así que un lector externo no puede distinguir "a mitad de camino" de "recién terminó" solo mirando ese archivo. La señal real de "Fase 2/3 completó" es el retorno `Ok(Ok(()))` de `run_pipeline` dentro de `lanzar_procesamiento_job` (`audio_handler.rs`) — ya existe hoy, antes de que se dispare `run_embedding_phase`. Setear `transcript_ready = true` ahí mismo evita: (a) agregar un 5to estado a `JobStatus` que obligaría a tocar cada `match` existente sobre ese enum, y (b) cambiarle el schema a `checkpoint.json` para que cargue información que no necesita para su propio propósito (crash recovery de Fase 2/3). `status` sigue representando el resultado combinado (`Completed` solo si Fase 2/3 **y** Fase 4 terminan bien, `Failed` si cualquiera falla); `transcript_ready` responde en concreto "¿tiene sentido servir `GET /transcript`" independientemente de si los embeddings fallaron después.

## Nuevos endpoints REST para el cliente web (diseño — sin implementar, 2026-07-29)

Definido con el usuario para desbloquear el cliente web: wrappers REST simples bajo `/api/*` (mismo Axum, sin microservicio nuevo) para que el browser no tenga que hablar el protocolo MCP completo (handshake `initialize`/sesiones) solo para lectura. Cada endpoint reusa directamente las mismas funciones internas que ya llaman las tools de MCP (`rag::retrieval::search`, `rag::generation::rag_answer`, `audio_pipeline::job::load_job`) — nunca duplicar esa lógica. Alcance acordado explícitamente: **solo lectura por ahora** (sin delete/cancel de jobs — ver nota al final). Todos dependen del fix de `status` de arriba para ser realmente útiles, aunque no todos lo requieren para poder implementarse.

- [ ] **`GET /api/jobs/{job_id}` — status/progreso de un job.**
  - Devuelve `job.json` vía `load_job` (mismo validador de UUID que ya usa `resume`), pero **filtrando** `audio_path`/`transcript_path`/`checkpoint_path` — el mismo gap ya documentado arriba para `list_audios`/`get_audio_metadata` de MCP aplica acá; no repetirlo en el endpoint nuevo.
  - `404` si el job no existe o `job_id` no es un UUID válido (mismo comportamiento que `resume`).
  - Siempre `200` si el job existe — nunca `202`/`400`/`425`/`500` para comunicar el estado del dominio (ver decisión de `GET /transcript` abajo, mismo criterio: el body ya tiene `status`, no hace falta que el código HTTP lo repita).
  - Incluye `transcript_ready` (ver ítem nuevo en la sección de arriba) además de `status`, para que la UI pueda saber si ya tiene sentido llamar a `GET /transcript` aunque `status` todavía no sea `Completed` (ej. embeddings en curso).
  - Diseño abierto a decidir en la implementación: ¿agregar también `last_chunk`/`processed_seconds` leídos de `checkpoint.json` (ya existen, baratos de leer) como progreso más fino que el enum de 4 estados?
  - **Gap documentado, no resuelto acá — "jobs atascados"**: si el proceso completo del servidor muere (no un error de Rust capturado dentro de `run_pipeline`/`run_embedding_phase`, sino el binario entero cayendo), ningún código corre para marcar `Failed` — el job queda en `Processing` para siempre, indistinguible de "está transcribiendo activamente un audio de 5h que legítimamente tarda horas". La señal correcta para detectar esto **no** es `created_at` (un audio largo puede tardar horas de forma legítima) sino el `mtime` de `checkpoint.json` (se reescribe tras cada chunk de ~30s, así que "hace cuánto no se mueve" sí mide actividad real) comparado contra un umbral. **Decidido explícitamente no fijar ese umbral ahora**: depende de cuánto tarda un chunk en la máquina real corriendo el proceso (CPU, carga concurrente, etc.), así que cualquier número fijo sería una verdad relativa a un hardware específico, no una garantía general — documentar el enfoque acá y en el README (ver nota agregada ahí) en vez de codificar un valor arbitrario. Implementar recién cuando haya una medición real de cuánto tarda un chunk en condiciones normales.
- [ ] **`GET /api/jobs` — listado de jobs (equivalente REST de `list_audios`).**
  - Mismo filtrado de rutas de disco que el punto anterior. Extraer `mcp::listar_jobs` a un lugar no específico de MCP (ej. `audio_pipeline::job::list_jobs`) para que la tool MCP y este endpoint compartan el mismo `read_dir` + `load_job` por entrada, en vez de duplicarlo.

- [ ] **`GET /api/jobs/{job_id}/transcript` — contenido de `transcript.jsonl`.**
  - Servir en streaming (nunca leer el archivo completo a un `String` antes de responder, mismo principio del resto del pipeline), aunque en la práctica ~600 líneas por audio de 5h no es un volumen que amenace el límite de RAM — la decisión de formato acá es más de ergonomía de API que de recursos.
  - Decidir antes de implementar: ¿servir el `.jsonl` crudo (`application/x-ndjson`, más fiel/barato) o parsear a un array JSON (más cómodo para `fetch().then(r => r.json())` en el browser, a costa de parsear+re-serializar todo el archivo)?
  - **Decidido — contrato para contenido vacío/parcial**: siempre `200` si el job existe (`404` solo si no existe, mismo criterio que `resume`), nunca `202`/`400`/`425`/`500` para comunicar "todavía no hay nada".
